## 1. IP v2：菌冢（在 v1 方向 A 的基础上融合）

一句话世界观：大老爷死后埋在地下，吃他的菌丝长成了神，叫「圣菌」。虫子们为它建起一座哥特式的地下菌冢。在信徒眼里，被菌吞掉就是成圣。丸子头顶的蜡烛是菌唯一害怕的火。

- 机制与世界观咬合：
  - 体力就是蜡烛长度。
  - 体力耗尽后菌开始长到身上，这就是腐化。
  - 腐化满了就是死亡，教团称之为"恭喜成圣"，这是黑色幽默的落点。
- 视觉支柱：
  1. 圣光对霉暗：暖色烛光与金箔，对比青黑的霉暗，再用冷色的生物荧光点缀。
  2. 哥特建筑是长出来的：拱券是菇柄，肋拱是虫壳与骨，彩窗是甲虫翅鞘（会虹彩变色），玫瑰窗是菌褶。
  3. 可爱的圆：主角和小怪都圆滚滚、豆豆眼。恐怖感来自语境、尺度和菌。
  4. 神秘学符号：菌丝在地面上长出炼金法阵，弹力法阵和符文柱被激活时会发光。
  5. 死亡的温柔：葬礼花、缎带、蜡泪、尘埃、圣咏。
- 角色谱系：
  - 祈祷螳螂当祭司，骷髅天蛾当修女，圣甲虫守门。
  - 萤火虫是游魂，玉蝉是重生圣物。
  - 冬虫夏草信徒头顶长出子实体，像光环一样，这就是"虫草圣徒"。
- 界面风格：圣物匣与祈祷书。
  - 底板是漆黑底配金色花丝，宝石是甲虫翅虹彩，提示框是羊皮纸配泥金首字母。
  - 生命是一瓶圣液，体力是蜡烛，腐化时霉斑会真的爬上界面边框。

## 2. "最先锋"的视觉技术栈（拒绝老画面）

我们要避开的老派做法：

- 平涂小色板精灵
- 满屏黑描边
- 死光照
- 镜头一动像素就抖

我们要做的：

| 层 | 做法 |
|---|---|
| 相机 | 内部 640×360 渲染，相机吸附像素网格，放大时做亚像素补偿，镜头丝滑但像素不游动 |
| 材质 | 程序化色带着色（每种材质 3–5 档），色带之间用蓝噪声抖动过渡；甲壳与彩窗用薄膜干涉虹彩；蜡做次表面透光；黑水做湿润高光 |
| 光照 | 低分辨率延迟光照，几十盏烛光与荧光同时存在；地面用 2D 辐射级联全局光照（2024–2025 年流行的技术），烛光会在石地上晕染、渗色、被墙挡出软阴影 |
| 大气 | 体积孢子雾 + 光柱（彩窗投下的彩色光柱是首领房的招牌镜头），雾也做像素量化 |
| 描边 | 深度 + 法线 1 像素描边，用同色相的暗色而不是纯黑，凸起折边提亮 |
| 后期 | 像素级泛光、按区域生成的调色、轻微胶片颗粒、重击时的色散 |
| 打击感 | 冲击帧（1–2 帧反色剪影 + 速度线）、顿帧、镜头震动、弹簧回弹、满屏跳字聚合 |
| 动画 | 全程序化：西瓜虫 14 条腿用 IK，触角用弹簧，蜷球时分节甲壳逐节翻卷成球；挤压拉伸；布料与垂根用 Verlet |
| 特效 | GPU 粒子直接画进像素层：孢子、余烬、蜡泪、圣液飞溅、魂火；地面贴花会累积（蜡泪、焦痕、圣液） |
| 图标 | 约 190 件物品都有程序化 3D 模型，图标用同一条像素管线实时渲染出来 |
| 界面 | 程序化 SDF 哥特边框、像素对齐、弹簧动效；字体用原作同款开源「缝合像素 12px」（OFL 协议可商用），裁剪成子集，这是唯一的外部资源 |
| 音频 | WebAudio 程序化合成：甲壳磕碰、蜡与铃、管风琴、八音盒、圣咏铺底 |
| 体积 | 资产全部由代码生成，整包预计小于 10MB，打开就能玩 |

内部美术参考（只给评审代理对照用，不进游戏）：t3ssel8r 的 3D 像素、《Animal Well》的光与粒子、《Blasphemous》的神圣哥特、《Hollow Knight》的虫与菌、《Cult of the Lamb》的可爱邪典、《Inscryption》的神秘氛围、《Balatro》的界面打击感。

## 3. 自动化工作室：怎么组织几百个子代理

### 3.1 总体结构

- 我是总控：一个阶段拆成若干"波次"，每一波是一次 Workflow 运行。
- 每一波结束后，我读报告、更新任务板，马上开下一波。
- 状态全部落在仓库文件里（`studio/BOARD.md`、`studio/STATE.json`、`studio/reports/`），我的上下文被压缩后也能无缝接着跑。
- 中途中断就用 runId 续跑，已完成的子任务直接复用结果。

### 3.2 每个任务的流水线

1. **规划师**：把本波目标拆成任务卡。每张卡包含可改动的文件范围、依赖、引用的规格条目、验收标准、是否需要视觉评审。
2. **开发代理**：在独立 git 工作树里开发（共享主目录的 node_modules，不重复安装），只改自己范围内的文件。
3. **自测**：类型检查、单元测试、规则对表测试；视觉任务还要跑截图机，亲自看截图。
4. **代码审查员**：对照规格查正确性、确定性（预览必须等于结果）、性能、越界改动。
5. **美术评审团**（视觉任务）：三位评审分别从构图光影、角色动画、界面设计三个视角打分。必须每人 ≥ 8/10 才算过，没过就附具体修改单打回第 2 步。最多 3 轮，仍不过就升级给我处理。
6. **集成员**：把通过的分支按依赖顺序合进主干，解决冲突，跑全量回归，打标签。
7. **QA**：机器人对局、性能计、版式对位、视觉回归，再加一个完整性审查（"还缺什么"）。发现的问题变成下一波的任务卡。

### 3.4 让代理"看得见、测得出"的工具（P1 先做）

- `npm run shots`：Playwright + 本机 Chrome（RTX 5060 Ti）。用网址参数直达任意场景和状态（例如 `?scene=combat&seed=3&aim=45`），批量出截图给代理看。
- `npm run bot`：无头规则模拟，机器人整局对打，统计崩溃、卡死、伤害分布、通关率。
- `npm run parity`：数值对表（规格里的测试向量）+ 界面版式对位（我们的控件矩形对原作矩形）。
- `npm run perf`：脚本化场景测帧时间与绘制调用，分高、中、低三档。
- 视觉回归：新截图对比上一版已批准的基线，变化要美术评审签字。

## 5. 什么叫"做完"（全部满足才停）

1. Demo 里能玩到的界面、系统、内容全部就位。数值与原作导出表逐条一致，对表测试 100% 通过；例外项要写明原因。
2. 全流程可通：新手关 → 营地 → 冒险 → 击败首领 → 结算 → 回营地，存档可续。
3. 1000 局机器人对局 0 崩溃、0 卡死。
4. 性能：PC 1080p 稳定 60fps；中端手机开低档画质 ≥ 30fps。
5. 6 张北极星画面过美术评审，每位评审都 ≥ 8/10。北极星画面是：作战墓室、首领彩窗、地图页、营地、背包与提示框、出殡弹珠。全部界面也要过评审。
6. 交付物：单文件 H5 包 + 可部署的网页版。
