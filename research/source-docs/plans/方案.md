**反弹构筑测试室：极简 HUD、真实装备与属性验证方案**

版本：2026-10-27 / 方案待审阅。当前只完成资料与代码核对，没有开始本方案的运行代码改造。

**target：做一个你能亲手验证构筑的可玩原型。**

打开固定房间，看到现有甲壳虫骑士；在左侧查看角色或背包，把真实装备拖到右侧两列装备区；点击物品查看真实词条；发射角色后看到装备充能、发动、伤害与联动；用 P 面板改变属性，再重复同一个测试，结果必须按规则改变。

这轮沿用旧工程的极简点、线、面风格：深色底、清晰文字、细线边界、少量功能色、程序图标。保留原有角色、房间、翻滚、反弹及战斗表现。SUNBURST、哥特装饰、新贴图和影片制作不进入这一轮。

游戏长期方向仍是反弹战斗、装备空间构筑、带死亡风险的收益取舍与长期成长。本轮验证其中最重要的战斗和装备模块，后续再接商店、锻造、格子附魔、死亡结算与关卡循环。

**一屏的信息顺序与布局**

以20:9横屏手机为目标，候选逻辑尺寸1200×540。界面独立清晰排字，场景继续用现有渲染器；不把整屏文字跟随战场一起降采样。

```text
┌──────────────────┬────────────────────────────┬────────────────┐
│ 角色名／等级      │ 布置／测试状态   开始／重置  │ 装备           │
│ 生命、体力、护甲  │                            │ ┌────┬────┐   │
│ 腐化／经验        │     原有角色与固定房间     │ │    │    │   │
│ [角色] [背包]     │                            │ │ 两列真实格 │ │
│                  │     木桩、轨迹、伤害反馈   │ │    │    │   │
│ 属性列表         │                            │ └────┴────┘   │
│ 或单列背包       │  最近发动提示／展开记录    │ 物品充能反馈   │
└──────────────────┴────────────────────────────┴────────────────┘
```

- 左侧约26%，中央约55%，右侧约19%；这些是首轮布局参数，用实际800×360和1000×450窗口校正。
- **常驻第一层**：生命、体力、当前护甲、当前布置/测试状态；等级、腐化、经验作为紧凑辅助信息。
- **角色 TAB**：实际属性，按进攻、生存、行动、状态上限分组；首屏显示最常用项，其余滚动查看。没有独立“属性”TAB。
- **背包 TAB**：单列真实占格，可滚动；拖动物品时显示完整占地与落点。物品名称和选中详情辅助识别，图标不必精致。
- **右侧装备**：两列始终可见。候选测试容量为2列×6行，12格全部开放；这是测试参数，不是正式成长与容量定案。
- **详情**：点击固定选中，展示名称、品质、宽×高、标签、技能条件、当前数值、充能/次数；同时只打开一个详情框，开始拖动时收起，避免遮挡落点。
- **阅读基准**：800×360下正文18px、关键数值20px、主按钮至少48px。长词条在详情里换行/滚动，不靠整体缩小字号容纳。
- **点线面语言**：背景与选中面有明确层级；普通边框克制，主操作/选中高对比。蓝色资源、红色危险、可放置/不可放置还要用轮廓或符号区分，不能只依靠颜色。

**空间规则：物品尺寸真实，二维变化明确**

尺寸统一按“宽×高”标注，从数据读取。本次选定物品在源核心中为1、2、3连续单位格，对应当前投影1×1、1×2、1×3。旧剑为1×2、旧长袍为1×3；用户举的2×1是示例，不作为擅自旋转源物品的依据。这轮不新增物品旋转机制。

两列装备是我们的新组合方式，必须有真实二维坐标，建议本轮采用以下确定性规则：

1. 通用“相邻”指占用格共享边的上下左右物品，不包括对角；同一物品接触多个格也只算一次。
2. 原技能明确写“上方/下方”的，仍保留方向限定。UI与核心的上下坐标统一转换，不能颠倒。
3. “最上/最下”跨列并列时，先按方向行排序，再按左列、右列及稳定物品实例顺序去重；该规则属于新增二维适配，写入测试契约。
4. 背包和装备空间分开；背包里的相邻卡片不得被当作战斗装备邻居。
5. 越界、重叠和非法目的格拒绝移动；原物品保持原位，不复制、不吞物品。本轮先不增加拖放交换/自动挤位等额外交互。
6. 前端预览和核心落格调用同一占格判断。右列装备必须真正参与充能、技能筛选和战斗。
7. 合法行/列从每个容器的实际容量生成，不能沿用固定0–9行或只有0列的命令范围。验证1×1可放在测试背包第47行，1×3从第45行开始合法、从第46行开始越界（均为从0计数）。

24件总计44个单位格。默认提供每组4件的测试预设；P目录可以按需加入。为满足一次放入全部物品的测试需求，提供明确标为测试用的1列×48行背包和“一键放入24件”；单列滚动，正式背包容量不据此定案。

**从背包拖到装备，必须完整走过这条链**

`按下物品 → 确认拖动 → 实时占地预览 → 松手 → 核心检查并移动 → 卸下/装备钩子 → 更新属性与技能挂载 → UI读取新状态 → 短落位反馈`

- 点击与拖动分开：点击打开词条；鼠标超过约5px位移进入拖动；触屏采用约180ms长按进入拖动，提前明显纵滑交给背包滚动。这些是首轮调校值，实际操作后调整。
- 拖动物品始终保留源物品身份，源格显示轻量占位；手指/鼠标移动直接驱动拖影位置，不加跟手延迟。
- 可落格显示完整占地轮廓；不可落格显示拒绝符号。只有核心接受命令后才提交位置并播放落位反馈。
- 松在无效位置、按Esc、失去指针、屏幕方向变化时恢复原位；从背包拖过战场不会发射角色。
- 核心在抓起/卸装前做纯粹的落点预检查；非法移动不能先触发卸装再回滚。失败前后同时核对位置、Buff、技能挂载、充能和RNG全部不变。
- 第二根手指不能抢占第一根手指。详情里的对象、被拿起的对象和核心命令中的对象必须相同。
- 卸回背包后，装备带来的效果必须按源规则移除；不能只让卡片位置发生变化。

**测试室的状态与P工具**

| 状态 | 玩家可做的事 | 核心处理 |
|---|---|---|
| 布置 | 拖装、查看词条、调整属性、选择预设、放置木桩 | 暂停战斗推进；通过测试适配层和真实创建/装备流程修改状态 |
| 开始测试 | 应用布置并发射角色 | 按源流程进入战斗，刷新装备目标缓存与临时状态；使用真实反弹系统 |
| 试射 | 观察充能、发动、伤害和连锁；可查看详情 | 锁定拖装，避免在一次发动过程中换掉依赖；UI不控制装备何时发动 |
| 回到布置/重置 | 改组合再试 | 保留布置定义，清理本次临时增益/状态；按同一种子重建或重入测试，便于对照 |

不直接解除正式冒险的战斗整理限制。测试能力隔离在工作台入口中，不读取/覆盖正式存档。

P面板也要有手机可点入口，内容收敛为：

- **装备**：24件搜索目录、品质、加入背包/装备、移除、六组预设、全部放入测试背包。
- **角色**：真实基础属性编辑、当前/上限分开、来源解释、恢复基线；已有天赋可先提供列表式查看与测试挂载入口，完整网状天赋界面后续做。
- **木桩**：1个/3个固定目标预设，生命、当前护甲、伤害减免、格挡/闪避层等真实测试字段，一键重置。保留真实被击中、受伤和状态处理，仅让其不移动；需要测试这些防护机制时可调用一次真实受击流程。
- **运行**：开始测试、回到布置、重置种子、恢复资源、可选慢速观察。
- **记录**：查看最近事件、按装备筛选、清空记录、导出一次测试结果。

新格子附魔、完整天赋树界面、锻造经济和整套冒险循环不挤进首个两小时核心交付；接口保留，后续围绕这个测试室逐项加入。

**属性必须有机制证据**

建立完整属性映射表：`显示名 → 源字段与所属对象 → 单位与公式 → 当前生效值 → 实际消费函数 → 生命周期 → 运行验证`。

角色属性、物品自己的属性、全局探索修正、状态层数分别识别。物品的“基础伤害20”可能是该技能的参数，不意味着人物基础伤害要从30变成50。词条说明与日志都要指向正确的数值拥有者。

| 属性/机制 | 最低验证方式 |
|---|---|
| 基础伤害、各伤害倍率 | 同种子、同目标、同装备、同发射，只改一个数值；实际伤害按对应公式变化 |
| 会心率、会心倍率 | 用0%/100%两端及固定种子验证真实会心分支，再检查倍率改变后的实际结果 |
| 生命上限、治疗及治疗加成 | 真实受伤后用药/发动治疗；检查上限、当前生命、实际治疗量及次数 |
| 强固、护甲、减伤、格挡/闪避层 | 走真实受击链，检查生命与护甲分摊、状态层消费和减伤结果 |
| 体力、消耗减免 | 一次真实测试结束后核对资源消耗；不把装备充能当体力 |
| 弹射距离、攻击距离、质量 | 比较真实轨迹、目标判定或碰撞结果，而非只检查面板数字 |
| 充能加成、灌注、连击、投射分裂 | 检查源事件、充能前后值、发动次数与投射物数量 |
| 流血、燃烧等持续效果 | 核对施加条件、后续结算和归因；直接伤害击杀不能冒充持续效果击杀 |
| 探索/收益类全局属性 | 核对各自真实消费方并用对应定向测试证明；不因木桩战斗没有掉落/商店就编造面板效果 |

你举的“命中率”目前没有核到独立概率属性，当前代码中的“攻击命中”是结果布尔。方案先接通真实碰撞与命中判定，并把“新增命中率”列为待定义的新规则；不创建一个没有消费者的百分比。其他废弃字段、分类标签也不能当成现行角色数值。

全部有效角色属性都进入覆盖矩阵。战斗类是本轮测试室的必须验证项；其他场景才消费的属性保留其真实入口与验证状态。数据缺项、未实现、已实现但未验证分别列明，不能合并为“已完成”。

反复打开词条和读取属性还要验证游戏状态摘要与RNG不变，避免“看面板”本身改变模拟结果。

**让玩家看懂真实发动**

从核心事件/执行记录订阅只读反馈，必要时加诊断事件，不改变算法、RNG或事件顺序。每条记录至少有模拟时间、来源物品、触发条件、目标和实际数值变化。

例如可以观察：实际反弹 → 旧长袍条件满足 → 某件装备充能增加 → 该装备发动 → 目标受伤。UI的亮边、跳字、连线只能由这条真实事件链驱动；单纯“充能条满了”不等于已经执行技能。

界面给出小范围的物品亮边、充能刻度变化、源与目标的短连线以及场上伤害/治疗数字；完整明细放在可展开记录中。高频事件可合并显示，但日志保留原次数和归因。

**交互动画：短、清楚、跟手**

下面是新原型的起始调校参数，不是声称测得原作帧参数，也不改动已有英雄反弹/受击的源时序。

| 动作 | 起始方案 | 检查重点 |
|---|---|---|
| TAB切换 | 选中状态立即更新；内容约100–140ms淡入/4px短位移 | 不等待动画才接受下一次操作，不挪动战场 |
| 拿起物品 | 约80ms轻抬起/1.03倍放大，拖影直接跟手 | 没有橡皮筋延迟；完整占地可见 |
| 合法落位 | 核心接受后约120ms收敛到格子 | 不长时间弹跳，不影响再次拿起 |
| 拒绝落位 | 约140ms回到原位，目标短暂拒绝提示 | 数据从未丢失或复制，理由能看见 |
| 详情 | 点击立即选中，约100ms展开清晰内容 | 一次一个信息框；读到谁就拿起谁 |
| 装备发动 | 约90ms轮廓反馈，短数值/连线反馈 | 对应真实发动事件，不凭前端计时器假播 |

研究参考已落到具体做法：

- [Dead Cells 开发者 GDC 复盘](https://media.gdcvault.com/gdc2019/presentations/Benard-Sebastian-DeepCells.pdf)：操作应理解玩家意图，控制细节不能成为额外挑战。这里用于确定跟手、取消和不阻塞输入的原则。
- [Dead Cells 官方无障碍/UI更新](https://deadcells.com/patchnotes/29)：HUD与文字可调大小，协同效果图标能提示关联，暴击反馈应清楚而不刺眼。这里用于大字、协同高亮与克制反馈。

这些来源不证明我们已经复制了它们的动画曲线。实现后要录下普通鼠标/触摸操作，实际观察拿起、跨栏、落位、取消和连续快速操作，再调节手感。

**两小时首轮冲刺的分工与顺序**

两小时从方案确定、进入实施后开始计。目标是可玩的测试室和可复查结果，时间估计不替代验收。

| 时间 | 并行工作 | 交付检查点 |
|---|---|---|
| 0–10分钟 | 主协调者冻结数据/尺寸/二维规则/测试状态契约，建独立工作树和入口 | 所有人用同一数据模型，避免末尾拼装才发现接口不一致 |
| 10–60分钟 | A：极简HUD/TAB/拖放/详情/动画；B：二维占格、邻接、装备生命周期；C：24件目录、属性/木桩测试适配与预设；协调者接原房间和动作系统 | 首个物品通过真实命令完成背包→右列→背包；开始测试时实际发动 |
| 60–90分钟 | 合并三条线，逐组验证充能、护甲、治疗、流血、投射、火系；优先补三件缺直接测试引用的物品 | 逐项记录拖装、主要技能、卸下与协同结果，修断链 |
| 90–110分钟 | 属性因果对照、两列边界、多格去重、触屏滚动/拖放隔离、800×360及1000×450检查 | 明确哪些机制已实际通过，哪些仍有问题 |
| 110–120分钟 | 针对性回归、构建、操作录像、交付包、提交与校验记录 | 可打开的原型＋P工具说明＋24件/属性验证表＋已知问题 |

代码职责：A只负责新工作台UI/输入/视图；B负责库存、邻接和相应核心测试；C负责内容清单、测试适配、预设与机制验证；协调者负责共享契约、入口、房间接入和最终整合。先写接口再并行，禁止多个代理同时重写相同核心文件。

七项全局属性的 `src/core/sys/run/index.ts` 初始化修复由协调者单独负责，C验证真实消费路径；B不同时修改该文件。

两列适配和真实属性链是关键路径。若检查点暴露问题，先收敛装饰与额外工具，不牺牲真实拖放或发动来凑数量。到两小时应明确交付状态，例如“24件中X件已通过哪些链路”；未通过项继续作为具体缺口，不用图标数量代替机制完成。

**验收时，你要能亲手完成的事**

1. 打开固定房间，使用原有角色发射、翻滚、反弹。
2. 切换角色/背包，生命等状态常驻且字号清晰。
3. 从P目录或背包取物品，准确放到右侧两列；1×2、1×3不会少占格。
4. 重叠、越界、取消拖动均不丢失物品；拖过战场不误发射。
5. 点击同一物品能看到正确的动态词条、尺寸、状态和触发条件。
6. 开始测试后，能看到真实充能/发动和对应伤害、护甲、治疗、状态或投射物。
7. 卸下或移动邻接物品、重新开始测试后，真实结果按规则改变。
8. 改变真实属性，在同种子对照中改变实际结果；没有消费者的字段不能伪装成有效属性。
9. 六组至少各有一条可复现的实际协同证据；24件每项技能分别标注已触发验证、条件未满足、未验证或缺口。
10. 原型、录像、验证记录绑定同一源码提交和交付包哈希；浏览器模拟与真机验收分开记录。

本轮交付是运行原型，不是概念图。它首先用于你判断“摆装备、看发动、改属性、再打一发”是否成立；完整经济与关卡平衡不由这次木桩测试得出。

**proposals**

- 2×6装备测试容量、1×48全目录测试背包、通用四方向共边邻接、明确整备/试射状态、上述动画初值，均是本方案提出的原型参数，尚非正式游戏平衡结论。
- 先以列表式P工具检查玩家系统；后续的天赋树、格子附魔、商店/锻造和冒险循环复用该测试基础。

**needs**

- 本方案进入实施前由用户审阅范围和新增二维规则。
- “命中率”等源内容未定义的独立属性需要另立规则，不能当作已经存在。
- 后续真实手机体验需要单独验收。本轮规划不声称两小时能证明所有装备组合平衡或完整原作一致性。

证据：`equipment-audit.json` 为24件逐项R2/源码映射；`core-readiness.json` 为真实模块与缺口审查。两份审查均为只读，本次未运行新原型、未修改工作簿、未提交付费素材任务。
