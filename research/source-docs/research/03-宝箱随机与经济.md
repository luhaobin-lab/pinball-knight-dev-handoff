# 宝箱、随机、品质与经济：原包算法说明

本册的唯一二进制基准是当前安装的 `CatapultHero-Win64-Shipping.exe`，SHA256 为 `ccd1db79c2eb3668242c4c10d271234963bc9dc1efa3ec0afddace444d1afcab`，大小153,626,624字节。蓝图及数据表来自本轮重新解包目录 `../provenance/extraction/dump`。TypeScript重构仅用于寻找线索，未作为算法正确性的原始证据。

完整可合并工作表在 `algorithms-tables.json`；其中每条包含原JSON路径、函数/字段定位、证据类别、使用状态和确认边界。原函数全文保存在 `evidence/`，字节码保留在新解包目录。下面解释开发时最容易误实现的差异。

## 1. “宝箱抽装备”至少有三种不同算法

`修炼系统.筛选物品生成` 先构建候选池。它遍历合成物品表的202条投影，但不表示每个宝箱均能抽到202条。

每一条必须同时满足当前总层数、制造需求、目标标签、排除标签、忽略标签、异品质过滤，以及英雄标签条件。空目标标签集放行；目标或/且为false表示任一，为true表示全部。制造需求为None时不加制造限制，-1具有“只有材料需求而没有物品需求”的特定含义。异品质过滤先查看背包与已装备物品；废品和附魔标签另有例外。

候选池建成后按数量参数分支：

| 参数 | 实际算法 | 随机来源 |
|---|---|---|
| 正整数N | 最多min(N,候选个数)次权重抽取，抽中后不删除候选，因此允许重复名字 | 本函数RandomStream输入的局部副本 |
| -1 | 先抽三列，每列4单位高度的尺寸序列；每个尺寸再从对应大小的候选子池随机抽名字 | 无显式种子的引擎随机 |
| -2 | 返回全部候选，保持表/数组顺序 | 无抽取 |
| 0 | 返回空 | 无抽取 |

填满模式不使用物品权重。它可能抽到一个没有候选的尺寸，原数组节点随后返回默认空项。不能自行改为“只选非空尺寸”，否则内容分布和随机消费均改变。

`函数库_工具.权重创建数组` 是另外的算法，每次抽取后删除行和对应权重，属于无放回。它用于奖励组等调用，不能代替上面的物品箱正数量模式。

## 2. 随机流按值参数是一个实质性的兼容点

新解包的原UFunction参数定义显示：

- `筛选物品生成.种子` 只有 `BlueprintVisible | BlueprintReadOnly | Parm`。
- `权重选取.Stream` 有 `ConstParm | Parm | OutParm | ReferenceParm`。
- `筛选物品生成` 的输出只有物品名数组，没有写回种子字段。

所以外层筛选函数拿到一个局部RandomStream副本，内部权重函数按引用推进的是该副本。它不是把传入的游戏全局流对象原地推进。此结论已由独立审查复核签名和完整正数量分支。

重写时若用共享JavaScript对象直接传递，会改变下一批物品种子及后续抽取。参考代码显式复制当前Seed；初始种子与当前种子不能混用。工作表“随机参数传递”保留所有5个包内RandomStream参数及原flags。

## 3. 品质不是“5%连续升级”

`生成卡牌` 的默认品质提升基准在游戏模式CDO为0.05。实际阈值：

`p = 品质提升基准 + 品质提升修正字段 × 0.01`

随后执行 `递减强化属性(3,p,生成品质)`。循环是 `i=0..3`，四次阈值分别为 `3p、2p、p、0`，每次判断 `RandomFloatInRange(0,1) <= 阈值`，成功便加1；没有失败即停止的逻辑。最终品质为min(提升后品质,4)。提升超过1级触发幸运的检查在封顶前。

最后一次阈值0不是完全不可能：本EXE的FRand由15位CRT随机数乘float32(1/32767)构成，包含0和1端点。raw=0时，这次比较会成功；raw=32767时FRand为1。

工作表“品质概率条件演算”准确统计每个阈值能接受的15位输入数，并合成四次独立均匀输入下的条件分布。该表明确声明独立输入假设。实际连续CRT状态有确定递推关系，候选池/起始品质/修正/其他调用也会改变实际结果，因此不能把该条件表冒充“全游戏固定出货率”。

## 4. 需要保留的原代码边界与异常行为

### 材料掉落两次抽取

`蓝图_动作游戏模式.添加材料掉落` 先拆分声明里的权重和行数组，但成功概率之后用的是 `Array_Random`，没有使用拆出的权重。每个成功尝试调用该数组随机节点两次：

1. 第一次选择A，保存为待写入的材料名字。
2. 第二次选择B，用B查询材料包当前数量。
3. 把 `trunc(材料包[B] + 1 + 材料掉落修正)` 写入A。

例如原来A=7、B=20，两次分别抽到A和B、修正0，实际结果是A=21、B=20，而不是A=8。这个差异已写入独立边界测试。它可能是原开发者缺陷，但复原资料不能擅自修正。

### 概率1不总是成功

`传统概率判断` 是严格 `< P`，而非 `<=P`。P=1在raw32767时失败。另一个引擎节点 `RandomBoolWithWeight` 则是正权重时 `W>=FRand`，权重非正不抽取。这两个节点不能互换。

### 权重池耗尽

`权重选取` 无结果时没有返回-1，out默认0；总权重非正使引擎整数范围不推进RandomStream。无放回的 `权重创建数组` 在池耗尽后仍按请求次数循环，可能继续追加默认空行句柄。零权重条目和空池都在资料中保留。

### 结果未使用也可能消耗随机

`生成卡牌` 在Select显式种子/随机种子之前已经执行一次 `RandomIntegerFromStream(global,2147483647)`，因此显式种子并不自动免除这次消费。

`BP_ManeActor.添加行动力` 的有效属性充能分支先执行 `RandomFloatInRange(.6,1)`，再根据“随机化？”选择是否使用其数值。随机化为false仍有一次消费；固定充能分支与僵直/行动力0提前退出不经过该调用。

## 5. 价格、金币和刷新

卡牌价格不是表里的“价格”字段本身。`BP_Actor_Card.更新价格` 读取价格的基础来源与包含永久来源的溢价：

```text
原始价格 = trunc(占格数 × 价格基础值 × 等级 × (1－购买折扣))
全价条件 = 非强制半价 且 属于未拾取牌 且 不属于仓库
当前价格 = (全价条件 ? 原始价格 : 整数除法(原始价格,2)) + trunc(溢价)
```

品质1/2/3/4对应等级1/2/4/8，来自卡牌升级入口L33843的 `trunc(pow(2,品质−1))`。免费物品由探索效果把当前价格覆写0，不应改动价格基础字段。

“物品默认价格演算”提供202条×4品质共808种默认情境，折扣为0，仅使用原基础溢价。它们是开发对照值，实际游戏报价仍需要当前来源、折扣、免费标志等条件。

金币/精核内部字段范围0..999，收入字段范围0..99。界面文案精核与内部金币是同一字段的命名映射，不是新造两种货币。

购买先验证活英雄、已揭示、可支付，再找装备空间，失败时再找背包空间；找到空间才扣款。分解/出售不只是删除卡片并加钱，还派发本物品“分解后”和其他物品“有物品被分解”等事件。

物品盒子刷新价格为 `trunc(来源能力消耗 + 刷新费用修正)`。刷新按钮可用条件是次数不等于0且金币足够。按钮先执行来源能力刷新回调，再减次数、扣钱。打开盒子初始化次数时，输入>0才加全局次数修正，否则写0；原部分描述中的“-1无限”不能替代这条实际逻辑。

## 6. 怪物/实体掉落与旧体系必须分开

当前 `BP_ManeActor.触发掉落` 先处理材料，再读取实体当前价格，取 `RandomIntegerInRange(0,trunc(价格×0.6))` 个货币。货币实体散射还有力度与方向随机。这些表现调用也可能影响后续CRT状态。

安装包另保留旧 `BP_Actor_Equip` / `数据表_装备` / `生成随机装备` / `添加装备掉落(新)` 体系。其中有等级偏移权重、品质权重、最近两次历史筛选和非酋保护。它不能与当前修炼物品生成公式混为一个算法。“旧体系”表示结构与当前202物品卡牌体系不同；是否自然可达仍需要引用链证据，不能仅凭目录或函数名称断言全部废弃。

## 7. 已从当前EXE核验的随机数层

1. `RandomFloatFromStream` wrapper直接包含LCG：Seed=Seed×196314165+907633515（32位回绕），取Seed右移9位构造float32尾数，再减1。该EXE使用右移9位，不应套用另一个UE版本的低23位实现。
2. `RandomIntegerInRangeFromStream` 在正跨度时用float32乘法和向零整数转换；所提取实现没有额外Min夹紧。非正跨度不推进。
3. `SeedRandomStream` wrapper在0x143ba3878调用一次CRT rand，然后把结果同时写入InitialSeed和Seed。
4. 已确认的启动srand调用在0x144224e78。普通分支先读取QueryPerformanceCounter，低32位传给srand；另有FixedSeed、UseFixedTimeStep条件分支。历史某次运行的QPC值与已发生的线程内rand调用无法从静态包恢复。
5. CRT递推与本机UCRT在6个种子、共1536次调用中一致；全会话调用交错和线程状态不因此得到证明。

全部793个蓝图的38,217个调用token中提取308个随机相关调用点，另列17个种子操作调用点。包括游戏逻辑和表现节点；这些是静态调用位置，不是一次运行的调用次数。

## 8. 原生PRD的验证范围

本轮没有启动原游戏。工具从当前EXE复制限定的数值例程到私有内存，保留其相对布局，接上本机CRT log/log1p和可控raw随机回调，运行独立算术测试。

原生批量算法使用几何跳跃和拒绝采样；每个open-interval均匀样本由3次15位raw随机构成。它不是把每次PRD尝试按普通for循环逐个roll。

独立编写的Python参考（不导入游戏重构代码）与以下原生输出一致：960组批量结果及精确raw消费、16组端点批量、36组概率量化、5组openUniform，共1017组。另有12组蓝图/公式边界测试。向量、代码、二进制范围与哈希全部保留。

CfromP的数学二分路径已按x64说明，容差5e−5、最多80轮；完整公共wrapper和TLS缓存外壳没有被此原生oracle执行。因此不能把1017组验证描述成整个随机系统所有路径均已等价。

## 9. 直接复用方式

- 使用原始表作为数据源，保留行顺序、原枚举、空映射、零权重及明确的默认值。
- 使用“随机与经济算法”表作为规则入口，跟随原函数JSON定位检查条件和执行顺序。
- 先运行 `scripts/verify_reference.py`；预期输出pass。该脚本读取本轮原生oracle向量并独立比较。
- 移植随机函数时先区分FRandomStream输入副本、FRandomStream引用、无显式种子CRT和原生PRD回调。
- 需要重现整局完全相同抽取时，还必须具备相同起始状态、同线程随机调用交错、同一池顺序和同浮点语义；当前资料没有伪造这部分证明。
